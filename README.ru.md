Просмотрщик IL/ASM и декомпилированного C# кода для .NET-сборок.

Основной режим — **одна панель с двумя выпадающими списками**: что показывать (`IL code`,
`Decompiled C#`, `Native ASM`) и для чего (`весь файл` или конкретный член). Панель открывается
один раз и переиспользуется, поэтому просмотр десятка методов не оставляет за собой десяток
вкладок.

Кроме неё есть обычные вкладки редактора на ту же информацию — там доступны штатный поиск,
свёртка и синхронизация выделения. Курсор в IL подсвечивает строку вашего исходника (по sequence
points из portable PDB), курсор в исходнике подсвечивает соответствующие инструкции IL (а панели C#
и ASM — тот член, к которому эта строка относится).

ASM-панель умеет читать код тремя способами: из **ReadyToRun-образа** (код лежит в самом файле — ни
процесса, ни пересборки, и это единственный маршрут, который показывает код другой архитектуры), через
**attach к вашему запущенному процессу** (у каждой инструкции видно, какую инструкцию IL она
реализует, а курсор ведёт в точную строку исходника) и через харнесс, который компилирует метод в
отдельном процессе. Плюс весь листинг можно собрать обратно в сборку через `ilasm` — ассемблер
поставляется вместе с расширением.

**Требования**

* **VS Code 1.90** или новее.
* **.NET 10 runtime** — движок запускается через `dotnet` и поставляется как
  платформо-независимая сборка. Более новый рантайм тоже подойдёт (`RollForward=LatestMajor`),
  более старый — нет.
* Для сборки из исходников дополнительно нужны **Node.js** и **.NET 10 SDK** — см.
  [Сборка и запуск](#-сборка-и-запуск).

## 🏁 Быстрый старт

**Установка.** В Marketplace расширения нет (`publisher: local`), поэтому оно ставится из пакета:

```bash
code --install-extension dist/ilasm-dotnet-1.0.0.vsix --force
```

Как собрать этот пакет из исходников — в разделе [Упаковка](#-упаковка).

**Первые шаги.**

1. Откройте проект с `.csproj` (или `.fsproj` / `.vbproj`) и поставьте курсор в метод.
2. `Ctrl+Alt+I` — справа от исходника откроется единая вкладка просмотра, код остаётся видимым слева.
3. Вид (IL / C# / C# low level / Native ASM) и область (файл / член) переключаются CodeLens-строкой
   над кодом или `Ctrl+Alt+Shift+I`.

Связка работает сразу: курсор в исходнике подсвечивает инструкции IL, курсор в IL — строку исходника.
Если связки нет, почти всегда дело в отсутствии PDB: что это значит, описано в разделе
[Что видно, когда что-то не так](#-что-видно-когда-что-то-не-так), а общую картину соберёт
`ILASM Dotnet: Show Diagnostics`.

## 📦 Что читается

Инструмент работает по метаданным и debug-информации, поэтому ограничения у него не «по версии
фреймворка», а по формату файла.

| Что | Поддержка |
|---|---|
| IL и декомпилированный C# | ✅ любая управляемая сборка, которую понимает reader метаданных: .NET Framework 2.0+ (`mscorlib`), .NET Core / .NET 5–10, netstandard, Mono; x86/x64/arm64. Проверено на реальном `Newtonsoft.Json` `lib/net45` — 511 типов, IL типа 2754 строки, C# 1116 строк |
| C#-синтаксис на выходе | ✅ задаёт декомпилятор, а не целевой фреймворк: `SetLanguageVersion` не вызывается, поэтому действует дефолт `ICSharpCode.Decompiler` 11.1.0.9782 — `LanguageVersion.Latest` (флаги фич C# 14: `ExtensionMembers`, `FieldKeyword`, `UsePrimaryConstructorSyntaxForNonRecordTypes`, `ParamsCollections`, `RequiredMembers`, `Utf8StringLiterals`…). Record и file-scoped namespace восстанавливаются даже из старого IL |
| ASM от JIT | ⚠️ работает, если рантайм, на котором запущен движок, может загрузить сборку. Это **не** рантайм приложения: у вас движок идёт на 10.0.11 (`RollForward=LatestMajor`), и код — от его JIT. Сборку net45 загрузить тоже получилось (через фасады), но экзотические зависимости на Framework-специфичные API могут не загрузиться |
| ASM из ReadyToRun-образа | ✅ без запуска кода, x64 и arm64, linux/windows/osx; для неподдерживаемой архитектуры (например linux-arm) — честная заметка вместо тихого отката |
| ASM живого процесса (ClrMD) | ⚠️ x64: декодер Iced жёстко 64-битный |
| Debug и Release | ✅ одинаково; PDB нужен **только** для видов по файлу и связки исходник ↔ IL. В Release (portable PDB по умолчанию с .NET 6) sequence points реже, поэтому берётся ближайшая размеченная строка в пределах 25 строк. `DebugType=none` → по типу/члену всё читается, а файловые виды честно пишут `; No debug information is available…`. Windows «full» PDB не читается вообще (поддерживается только portable) |
| NativeAOT | ❌ IL и C# — **нет**: в AOT-образе нет IL, тела уже машинный код, и это ограничение природы образа. **Машинный код метода — да**: ELF, символы с адресами и размерами плюс DWARF (`.debug_info` для имён, `.debug_line` для строк исходника) — см. раздел [NativeAOT: ASM без IL](#-nativeaot-asm-без-il). Требуется Linux и нераздетый образ; отладочную информацию публикация по умолчанию кладёт рядом в `Foo.dbg`, и вьюер находит её по `.gnu_debuglink` |
| `PublishTrimmed` (без AOT) | ✅ читается: IL на месте |
| `PublishAot` из редактора | ✅ проект с `<PublishAot>true</PublishAot>` читается **из образа**, а не из промежуточной `bin/**/<Имя>.dll`, из которой его собрали: код в них разный, и второй — не то, что исполняется. Если образа рядом нет (ещё не публиковали), берётся dll |
| `PublishSingleFile` | ✅ читается: файл — это нативный хост с приклеенной сборкой и манифестом в конце, поэтому сборка внутри распаковывается во временный каталог и дальше всё работает как обычно — IL, оба вида C#, ASM от JIT, связка со строками по PDB рядом с exe. Нативные куски (сам рантайм для self-contained) не распаковываются: метаданным они не нужны |

Под капотом: `ReflectionDisassembler` и `CSharpDecompiler` из **ICSharpCode.Decompiler 11.1.0.9782**,
метаданные — `System.Reflection.Metadata`, portable PDB — `PortablePdbInfoProvider` (ILSpy),
живой процесс — **Microsoft.Diagnostics.Runtime 3.1.512801** + **Microsoft.Diagnostics.NETCore.Client
0.2.661903**, дизассемблирование — **Iced 1.21.0** (x64) и **Gee.External.Capstone 2.3.0** (arm64),
сборка листинга обратно — `ilasm` 10.0.12 из `runtime.*.Microsoft.NETCore.ILAsm`.

```text

┌────────────────────────────┐             ┌──────────────────────────────────────────┐
│ extension.ts               │             │ Program.cs        — диспетчер вызовов    │
│  ├ IlasmDotnetDocuments    │  view/il    │ Views/IlViewService    — ReflectionDis-  │
│  │   схема ilasm-dotnet:   │◄───────────►│                           assembler      │
│  ├ SyncController          │  view/csharp│ Views/CSharpViewService — декомпиляция   │
│  ├ SourceLinkProvider      │  assembly/* │ Metadata/PortablePdbInfoProvider — PDB   │
│  ├ AssemblyTreeProvider    │  map/*      │ Metadata/AssemblyEntry  — PE, метаданные │
│  └ AssemblyLocator         │  live/*     │ Views/SourceIndex      — файл+строка→член│
│                            │             │ Live/LiveSession     — snapshot процесса │

└────────────────────────────┘             └──────────────────────────────────────────┘
```

Движок при старте отдаёт по одному JSON-вызову на панель:

| Панель | Вызов | Источник данных |
|---|---|---|
| IL | `view/il` | `ReflectionDisassembler` + sequence points |
| C# | `view/csharp` | декомпилятор ILSpy |
| ASM | `view/asm` | JIT рантайма через дочерний процесс |
| ASM живого процесса | `view/asmLive` | ClrMD: адрес, размер и JIT-маппинг из процесса |
| ASM из образа ReadyToRun | `view/asm`, `view/fileAsm` (по умолчанию) | таблицы R2R-образа + Iced/Capstone |
| Навигация | `assembly/*`, `map/*` | метаданные и portable PDB |
| Живой процесс | `processes`, `live/attach`, `live/detach` | `Microsoft.Diagnostics.Runtime` |
| Сборка обратно | `assemble/roundTrip` | `ICSharpCode.Decompiler` + `ilasm` |

Почему движок, а не чистый TypeScript: в JS нет ни IL-дизассемблера, ни декомпилятора C#,
ни чтения portable PDB. Вся тяжёлая работа делается на .NET, расширение отвечает за UI.

### 🔗 Как устроена связка видов

Каждая панель отдаётся как набор блоков (`MapBlock`), где текст связан с двумя якорями:

* `methodToken` + `ilStart`/`ilEnd` — привязка к телу метода (связывает IL и C#);
* `sourceFile` + `sourceStartLine`/`sourceEndLine` — привязка к исходнику (связывает оба вида с вашим кодом).

IL-панель отдаёт по блоку на инструкцию (offset → строка IL → строка исходника из PDB).
C#-панель собирается по членам, поэтому у каждого метода/свойства есть точный диапазон строк
и токен, по которому находится его IL.

Курсор в исходном файле проходит по **всем** открытым панелям: IL подсвечивается точно, потому что
у каждой инструкции есть строка исходника из PDB, а C# и ASM — на уровне члена, потому что это самый
точный якорь, который есть у этих видов (в ASM харнесса кода строк исходника нет вовсе, поэтому такая
панель не подсветится — это ожидаемо). Заодно панель **прокручивается** к подсвеченному месту, если
оно не видно (листинг всего файла — это сотни строк, искать в нём нужный метод вручную незачем);
прокрутка срабатывает только когда совпадение вне экрана, поэтому чтение вокруг подсвеченного кода не
сбивается. Это же работает и в обратную сторону: курсор на инструкции в IL/ASM прокручивает исходник
к её строке. Отключается настройкой `ilasmDotnet.syncScroll`. Связка срабатывает и при простом переходе
между вкладками: клик по `.cs` (или по панели) — это тоже движение по коду, даже если курсор не
сдвинулся.

## 🌳 Боковое дерево

В панели ILASM Dotnet сверху идёт раздел **с текущим файлом**, ниже — сборки проекта:

```text
▾ Catalog.cs                        2 type(s) · 24 member(s)
  ▾ Playground.Catalog              class
      .ctor()
      Add()
      Describe()
      LowStock()
  ▾ Playground.Item                 class
      .ctor()
      Name
      Value
▾ Playground                       1.0.0 · .NETCoreApp,Version=v10.0 · AnyCPU
  ▾ Playground.Catalog              class
      …
```

* Раздел следует за активным редактором: переключили файл — раздел обновился.
* Показываются **только те типы и члены, что объявлены в этом файле** (по данным portable PDB),
  а не весь публичный состав типа. Например, `MoveNext` из state machine сюда не попадёт.
* Клик по имени файла открывает панель просмотра для всего файла, клик по члену — для члена.
* Если выходная сборка не найдена или файла нет в отладочной информации, узел так и пишет,
  вместо того чтобы молча исчезнуть.
* Раздел появляется только когда активен исходный файл на диске: вкладки самого просмотрщика его не
  показывают.

## 🪟 Просмотрщик: одна нативная вкладка

Просмотрщик открывается как **обычная вкладка редактора VS Code** — один документ, который
переиспользуется для любого файла, вида и члена. Никаких webview и никакой россыпи вкладок.

```text
┌─ ILASM Dotnet ──────────────────────────────────────────────────────────────┐

│  …                                                                          │
```

### 🔀 Два вида C#

Декомпилированный C# бывает двух видов, и переключаются они той же строкой:

| Вид | Что показывает |
|---|---|
| `C# (high level)` | код так, как его написал бы человек: `foreach`, `using`, `switch`, `await`, лямбды, интерполяция строк, автосвойства |
| `C# (low level)` | то, что из этого сделал компилятор: циклы по `GetEnumerator`, `try/finally` вместо `using`, сравнения вместо `switch`, state machine вместо `await`/`yield`, анонимные методы вместо лямбд, отдельные объявления локальных переменных и никакого удаления мёртвого кода |

Низкоуровневый вид **всегда показывает compiler-generated members** — вложенные классы-состояния
(`<Evens>d__5`), display-классы лямбд, поля с именами вида `<>1__state` — независимо от настройки
`ilasmDotnet.includeCompilerGenerated`, которая управляет только высокоуровневым видом. Список членов в
переключателе области тоже следует за видом: в низкоуровневом в нём есть и сгенерированные члены,
иначе state machine, который видно на экране, нельзя было бы выбрать.

Зачем это нужно:

* сравнить синтаксический сахар с тем, что он порождает: например, `yield return` в высокоуровневом
  виде и класс-состояние с `MoveNext` в низкоуровневом;
* увидеть, что в сборку добавил инструмент, работающий на этапе сборки (Fody, PostSharp, генераторы
  исходного кода): высокоуровневый вид показывает то, чего нет в вашем файле.

**Правило переключения.** Входная команда, названная по файлу (`Open Viewer for This File`, клик по
файлу в дереве), открывает **файл целиком** — она не должна молча открывать один член. Узел дерева,
названный по члену, наоборот, сужает вкладку до этого члена, как и переключатель области, выбор
которого сохраняется при смене вида.

**У типа нет одного тела.** ASM-панель показывает код по методам, поэтому для **типа** она берёт тела
всех его методов (вместе с вложенными типами — так в листинг попадает и state machine итератора), а для
члена — его тело. Тип без тел (маркерный интерфейс, пустой класс) отвечает строкой «нет тела метода»,
а не ошибкой. И если вид почему-то прочитать нельзя, вкладка пишет об этом прямо: раньше неудачное
чтение оставляло на экране прошлый текст, и это выглядело как переключатель, который ничего не сделал.

**Клик по узлу дерева даёт то же рабочее место, что и вход из самого файла.** Узел — это метаданный
токен: по PDB (RPC `map/fileOf`) он разрешается в **исходный файл и первую строку** этого типа или
члена. Поэтому клик открывает `.cs` слева, ставит каретку на этот член (`map/fileOf` отдаёт строку)
и рядом, в правой колонке, показывает вкладку просмотрщика, **сразу в виде C#** — обозреватель сборки
там, где читают код, а IL и ASM переключаются одним щелчком в той же вкладке. Связка после этого
работает как обычно: курсор в исходнике подсвечивает и прокручивает вкладку, курсор в инструкции
ведёт в строку исходника. Токен разрешается и через **вложенные** типы, поэтому тип, всё тело
которого компилятор перенёс в сгенерированный тип (асинхронный или итератор), тоже находится, а
значок ASM у члена открывает нативный код того же члена. Если у сборки нет PDB, файла нет, но член
всё равно открывается: вкладка показывает его одного, а «весь файл» в переключателе области не
предлагается — выбор, который мог бы только не сработать, в списке не нужен.

**В контекстном меню `.cs`-файла одна команда** — `ILASM Dotnet: Open Viewer for This File`. Раз внутри
вкладки есть переключатель вида (IL / C# / C# low level / ASM) и области, отдельная кнопка на каждый
вид только повторяла бы его. Остальные входные команды никуда не делись: они доступны из палитры
команд (`Ctrl+Shift+P`) и из контекстного меню узлов дерева. Команды, которые открывают виды
**отдельными вкладками** (например, чтобы поставить IL и C# рядом), названы так и называются —
`Open IL and C# in Separate Tabs ...`.

**Где открывается.** Вкладка просмотра встаёт **справа от исходника**, а не поверх него: код
остаётся видимым слева, IL/ASM читается рядом. При повторном открытии вкладка остаётся в своей
колонке, переключение вида и области её не переносит. Если открытых редакторов нет вовсе, вкладка
занимает единственную колонку: просить «рядом» не с чем, а разделение оставило бы на экране пустую
колонку с приглашением открыть файл.

### 🔧 Свойства и их аксессоры

Областью можно выбрать не только метод, но и аксессор свойства — `get_Count`. В C# отдельного
аксессора не существует: панель показывает **свойство целиком** (`public int Count => _history.Count;`)
и пишет, к какому члену относится запрошенный аксессор. В списке области такой член подписан по
свойству — `Count (get)`, — а не как `get_Count()`. Панель IL при этом остаётся методом: аксессор
есть в метаданных, и его IL — это его IL. Блоки C#-панели сохраняют токен аксессора, поэтому связка
между панелями не теряется. В виде типа свойство печатается один раз: аксессор больше не выводится
рядом с ним безымянным блоком.

**Одна вкладка.** Переключение вида меняет язык документа (`il` → `csharp` → `il-asm`), из-за чего
VS Code пересоздаёт документ, а расширение сообщает, что содержимое устарело. Переключение области
перечитывает содержимое на месте. В любом случае вкладка одна.

### 🔒 Про read-only

Документ отдаётся через `FileSystemProvider` с `isReadonly` и `FilePermission.Readonly` в `stat`.
VS Code в этой версии **не** запрещает правки в буфере для такого документа (проверено в живом
хосте: `editor.edit()` возвращает `true`). Поэтому расширение дополнительно следит за изменениями и
тут же перечитывает содержимое — случайный символ не остаётся в просмотрщике. Ничего не сохраняется
на диск, так что испортить реальные файлы невозможно.

### 🚨 Что видно, когда что-то не так

Движок присылает к виду **замечания** (`notes`): у метода не осталось кода, в образе нет кода для этих
методов, PDB не найден, архитектура образа не поддерживается. Раньше их читал только старый
многопанельный режим. Теперь они видны в самой вкладке: в статусбаре появляется значок `$(warning)`
(в подсказке — полный текст), а если показать нечего вообще, причина пишется прямо в листинг.

Отдельный случай — файл, все тела которого компилятор перенёс в
сгенерированные типы: так выглядит любой файл с `async`-методом или итератором, потому что тело такого
метода живёт в сгенерированной state machine, а точки останова PDB приписаны ей. При настройках по
умолчанию видимых членов в таком файле нет, и раньше вкладка была **пустой** — пользователь видел
пустоту и не знал, что смотреть. Теперь показывается **тип, который объявляет этот код**: для
`Program.cs` с `async Task<int> Main()` это `public class Program` с восстановленным из state machine
`async`-методом, а сверху идёт `;`-заголовок, объясняющий, почему код выглядит именно так.
`"ilasmDotnet.includeCompilerGenerated": true` добавляет сгенерированные члены (`<Main>d__0`, `MoveNext`)
и в область файла, а вид `C# (low level)` показывает state machine так, как её выпустил компилятор.

**PDB проверяется на соответствие сборке.** Рядом с `.dll` может лежать PDB от другой сборки —
недосборка, скопированный файл. Раньше его точки останова читались как свои, и запрос падал с
`Read out of bounds.`; теперь идентификатор PDB сверяется с CodeView-записью сборки, и чужой PDB
просто игнорируется: вид открывается, но без строк исходника.

**Нативный образ — не сломанная сборка.** Если указать файл, который не является управляемой сборкой
(NativeAOT-бинарь, обычная нативная библиотека, просто текстовый файл), раньше всё заканчивалось
`Unknown file format.` — одинаково для всех причин. Теперь заголовок файла распознаётся до чтения
метаданных: `hello is a native ELF image for x86-64, not a managed assembly. A native image holds
machine code and no IL, so there is nothing for an IL or C# view to read here. A binary published with
NativeAOT looks like this: its method bodies exist only as native code.` Различаются ELF (Linux, с
указанием машины), Mach-O (macOS), нативный PE без метаданных (Windows) и «ни PE, ни ELF»; слишком
короткий файл тоже называется своим именем. Причина не теряется: она видна и в дереве — путь остаётся
в списке с пометкой `warning` и этим текстом, — и во вкладке (`; ILASM Dotnet could not read this view.`),
и в уведомлении при попытке открыть файл командой Open Assembly. Подробнее о том, что читается, —
в разделе [Что читается](#-что-читается).

### 🩺 Диагностика

`ILASM Dotnet: Show Diagnostics` собирает в один документ всё, что нужно для разбора проблемы: версию
расширения, версию VS Code, платформу и архитектуру, путь к `dotnet`, путь к движку, настройки
(`asmSource`, `asmOptimized`, `includeCompilerGenerated`, `syncScroll`, `ilasmPath`), есть ли attach,
что именно показывает вкладка и найден ли у сборки подходящий portable PDB.

### 🔄 Почему содержимое всё-таки обновляется

VS Code решает, перечитывать ли файл, по `mtime` и размеру из `stat`. Если они не меняются,
объявленное изменение выглядит как отсутствие изменения и документ остаётся со старым текстом —
это была реальная ошибка, которую нашёл тест в живом хосте. Теперь провайдер ведёт счётчик версии и
отдаёт его как `mtime`.

Панель обновляется сама, когда её содержимое перестаёт быть верным:

* **смена настроек** (`ilasmDotnet.includeCompilerGenerated`, `asmSource`, `asmOptimized`, `ilasmPath`) —
  расширение слушает `onDidChangeConfiguration`, сбрасывает кеш видов и перечитывает открытую панель
  вместе со списком членов области. Кеш при этом различает виды C# по настройке и ASM по источнику
  и режиму оптимизации, иначе панель осталась бы на прежнем состоянии;
* **сохранение `.cs`** — то, после чего обычно начинается сборка: кеши сбрасываются, дерево и панель
  перечитываются;
* **пересборка сборки** — движок держит открытые сборки в LRU-кеше, и раньше после сборки проект
  продолжал показывать старый IL. Теперь у записи кеша есть отпечаток файла (размер и время записи):
  как только файл на диске изменился, сборка открывается заново. Это проверяется сквозным тестом —
  файл сборки подменяется на другую сборку, и вид обязан показать ту, что лежит на диске.

## 🧰 Настройки

## 🔨 Сборка и запуск

```bash
npm install                 # dev-зависимости расширения
npm run build:engine       # dotnet publish в out/engine
npm run compile             # tsc --noEmit + esbuild
```

Затем F5 (`Run ILASM Dotnet`) — откроется Extension Development Host. Для проверки откройте
проект с `.csproj`, поставьте курсор в метод и вызовите
`ILASM Dotnet: Open Viewer for This File`.

Сборка без PDB тоже работает: IL и декомпилированный C# покажутся, но связка с исходником
будет недоступна — расширение честно сообщит об этом.

## 🧪 Тесты

```bash
npm test              # 555 проверок без GUI: манифест, маппинг, переключение, интеграция, движок
npm run test:inhost   # 85 проверок в живом хосте расширений VS Code (откроет окно)
npm run check         # compile + build:engine + test
npm run package       # собрать dist/ilasm-dotnet-<версия>.vsix
```

* `scripts/manifest.test.mjs` — валидность манифеста, меню, грамматики, путей, горячих клавиш
  (каждая ссылается на объявленную команду и не дублируется в том же контексте).
* `scripts/mapping.test.mjs` — юнит-тесты чистых функций связки (границы строк, нормализация путей, токены).
* `scripts/viewsession.test.mjs` — правила переключения: какой вызов движка соответствует
  состоянию, как подписаны вид и область, что содержит CodeLens-строка. Модуль
  `src/viewer/viewSession.ts` специально не зависит от VS Code.
* `scripts/extension.test.mjs` — загружает собранное расширение на стабе VS Code API, поднимает
  настоящий движок и проверяет команды, документы, переключение вида и области, подсветку, ссылки,
  дерево (включая узел с причиной, по которой файл не читается, и узел нативного образа с его
  методами), раздел текущего файла, **живой процесс** (`test/fixtures/LiveTarget` запускается и к нему
  делается attach), чтение ASM из ReadyToRun-образа, оба вида C#, смену настроек и перечитывание
  открытой панели, аксессоры свойств, подсветку и **прокрутку** связанных панелей (включая переход по
  вкладкам и настройку `ilasmDotnet.syncScroll`), клик по узлу дерева (он обязан попасть в единую вкладку
  с переключателем), round-trip через `ilasm` и обе настройки источника ASM.
* `scripts/smoke.mjs` — сквозная проверка движка на фикстуре `test/fixtures/SampleLib`
  (собирается автоматически), живой связки (`IL_xxxx` у каждой инструкции сверяется с IL-листингом
  того же метода), чтения кода из R2R-образов linux-x64 и linux-arm64 (размеры из образа сверяются с
  размерами из живого процесса, а arm64-листинг проверяется на отсутствие x64-инструкций), сборки,
  которая уже была прочитана и потом подменена на другую (кеш обязан заметить изменение), образа
  чужой архитектуры (листинг обязан сказать, чей это код), нативных образов (ELF/Mach-O/PE без
  метаданных из `out/engine/ilasm` — диагноз обязан назвать формат и сказать, что IL в файле нет,
  а управляемая сборка обязана по-прежнему читаться) и round-trip: листинг с
  `try/catch/filter/finally` обязан собраться тем же `ilasm`; `map/fileOf` проверяется на типе, на
  члене (включая строку, на которую встанет каретка), на типе, чьи тела лежат во вложенном
  сгенерированном типе, на неизвестном токене и на сборке без PDB. Фикстура `test/fixtures/AotTarget`
  публикуется как NativeAOT и проверяет нативный маршрут: адреса и размеры методов, имена из DWARF,
  строки исходника у инструкций, границы блоков и то, что раздетый образ честно сообщает о нехватке
  отладочного файла. Тот же `LiveTarget`, опубликованный одним файлом, проверяет разбор бандла:
  сборка из него читается, IL/C#/ASM и связка со строками работают, а файл с обрезанным манифестом
  отвергается. Фикстура `test/fixtures/Playground` добавляет то, чего у библиотеки нет: точку входа
  `async Task<int> Main`, тела которой компилятор перенёс во вложенный сгенерированный тип, — файл
  целиком из таких тел обязан показать код породившего их типа, а не пустоту, а PDB чужой сборки,
  положенный рядом, обязан быть проигнорирован. Фикстура `test/fixtures/R2RDebug` (net10.0) несёт
  вторую кодировку карты «инструкция → инструкция IL»: её ReadyToRun-образ пакует карту в битовые
  поля, тогда как образ `LiveTarget` (net8.0) пишет её подряд идущими числами, — обе формы обязаны
  читаться.
* `scripts/inhost/index.js` + `scripts/test-inhost.mjs` — то, что стаб проверить не может:
  запускается настоящий VS Code в изолированном профиле, определяется язык виртуальных
  документов, разрешаются document links, панели открываются бок о бок, панель ASM получает
  код от настоящего JIT, смена настройки обязана перечитать открытую панель, курсор в исходнике обязан
  **прокрутить** панель к нужному методу (и наоборот), клик по узлу дерева при закрытых редакторах
  обязан открыть одну вкладку с кодом этого узла, исходник слева с кареткой на члене и **не**
  оставить пустую колонку, значок ASM узла обязан показать нативный код, а attach к процессу в конце
  проверяется переходом из инструкции в точную строку исходника. Скрипт умеет проверять и
  **установленный VSIX**: `node scripts/test-inhost.mjs --vsix dist/ilasm-dotnet-1.0.0.vsix`.

## 🔬 Как получается нативный ASM

Панель ASM не эмулирует дизассемблер: она спрашивает код у того же JIT, который его исполняет.
Движок запускает **свой же** dll как харнесс с переменной `DOTNET_JitDisasm`, но вместо вызова
метода просит рантайм его скомпилировать:

```csharp
RuntimeHelpers.PrepareMethod(method.MethodHandle);
```

Поэтому ASM появляется **без выполнения тела метода** — это проверено тестом на фикстуре, где
метод пишет файл: файл не создаётся. Побочный эффект, о котором стоит знать: загрузка сборки
выполняет её module initializer, как и любая загрузка через рефлексию.

Что это даёт:

* реальный код рантайма, а не реконструкция — включая свёрнутые выражения и заинлайненный код;
* `FullOpts` при `DOTNET_TieredCompilation=0` (настройка `ilasmDotnet.asmOptimized`, по умолчанию включена), счётчик байт и статистику инлайна;
* tier 0, если отключить настройку;
* в шапке видно рантайм и вид кода: `; FullOpts, 77 bytes of code, runtime 10.0.11`.

Чего этот маршрут не даёт, и это честно указано в самой панели:

* **связка ASM → строка исходника**: `DOTNET_JitDisasmWithSource` в .NET 10 ничего не добавляет (проверено), поэтому без attach панель линкуется с IL и C# **по методу**. По инструкции связку даёт живой маршрут, см. следующий раздел;
* **оптимизация debug-сборок**: атрибут `[Debuggable]` запрещает оптимизацию, поэтому для Debug-сборки вы получите `MinOpts` — панель об этом прямо сообщает, а не молчит;
* **generic-методы**: компилируются с подстановкой `object` как представителя, поэтому код приблизительный;
* **методы, которые рантайм ещё не компилировал**: `PrepareMethod` компилирует не всё, поэтому панель сообщает, сколько методов осталось без нативного кода.

## 🧳 Публикация одним файлом

`dotnet publish -p:PublishSingleFile=true` даёт один исполняемый файл: нативный хост, к которому
приклеены сборки приложения и манифест в конце файла, говорящий, где что лежит. Ничего приложения в
самом хосте нет, поэтому для читателя метаданных это «не .NET-сборка», а для нативного маршрута —
раздетый образ без методов. Отсюда и разбор:

| Шаг | Как делается |
|---|---|
| Найти манифест | Маркера в файле нет: хост знает смещение заголовка «по сердцу». Поэтому ищется позиция, где записи манифеста разбираются и заканчиваются ровно на конце файла; запись говорит, где её байты и сколько их, так что чтение мимо почти невозможно (`Bundle/SingleFileApplication.cs`) |
| Проверить | Все данные записей лежат до манифеста, первая сборка начинается с `MZ` (для сжатого бандла — после распаковки её начала), а заголовок перед манифестом сходится по числу файлов и версии формата |
| Разжать | `EnableCompressionInSingleFile` (работает только вместе с `--self-contained`) кладёт файлы бандла deflate-потоками, поэтому размер записи в манифесте — это размер файла, а не занятых им байт; чтение распаковывает запись, а границы проверяются по занятым байтам |
| Распаковать | Сборки, символы и оба json-файла разворачиваются в `%TEMP%/ilasm-dotnet-bundle/<hash>`; каталог выводится из пути и даты файла, поэтому пересборка читается заново. Нативные двоичные файлы пропускаются: именно они делают self-contained бандл большим, а метаданным они не нужны |
| Читать | Дальше работает всё существующее: `AssemblyEntry` открывает извлечённую сборку, PDB ищется next to exe (`Foo.pdb`), ссылки резолвятся из каталога распаковки, JIT-харнесс загружает уже извлечённую сборку |

Что видно: обычный узел сборки в дереве, обычные IL/C#/ASM, связка со строками исходника — плюс в
тултипе статусбара строка «The assembly was taken out of the single file application Foo». Локатор
сборок для открытого `.cs` теперь ищет и `bin/**/<Имя>` (без расширения), а не только `<Имя>.dll`,
поэтому такой проект находится из редактора как обычно.

Проверяется фикстурой `LiveTarget`, которую smoke и тест расширения публикуют одним файлом, плюс
негативная проверка: тот же файл с обрезанным манифестом обязан быть отвергнут, а не прочитан
наугад. Второй фикстурой публикуется **сжатый self-contained** бандл (36 МБ, 171 файл): он проверяет
и распаковку записей, и то, что манифест находится не в начале хвоста, а по своему месту в большом
файле.

Выбор выхода проекта — отдельная маленькая задача, потому что после сборки в `bin` лежит несколько
файлов сразу: сборка, нативный образ, собранный из неё, и запускающий её хост. Именами их не
различить (у AOT-проекта dll — это **промежуточный** IL, а не то, что исполняется; у обычного проекта
хост — пустышка без кода), поэтому кандидаты (сборки вперёд, затем исполняемые файлы) перебираются
по читаемости: берётся первый, который оказался сборкой или образом с методами. Правило про
`PublishAot` при этом оставляет за проектом намерение: если он помечен как AOT, его образ идёт в
списке кандидатов первым.

## 🚀 NativeAOT: ASM без IL

У AOT-образа нет IL вообще — тела методов уже машинный код, поэтому ни IL, ни оба вида C# для него
невозможны (это ограничение природы образа, а не реализации). Зато возможен третий маршрут: читать
сам нативный образ.

Что он делает:

| Шаг | Чем читается |
|---|---|
| Контейнер | ELF: заголовок, таблица секций, символы, сжатые (zlib) отладочные секции — `Native/ElfImage.cs` |
| Отладочная информация | публикация AOT по умолчанию оставляет в образе только ссылку `.gnu_debuglink` на файл `Foo.dbg`; он ищется рядом и проверяется по CRC, как PDB у управляемой сборки — `NativeDebugFile.cs` |
| Методы | символы `Foo_Namespace_Type__Method` с адресом и размером, плюс человеческие имена из DWARF `.debug_info` — `DwarfNames.cs` |
| Строки исходника | DWARF `.debug_line` (программа, которую нужно выполнить, чтобы получить строки): адрес ↔ файл и строка — `DwarfLineTable.cs` |
| Дизасм | те же декодеры, что и в остальных маршрутах: Iced для x64, Capstone для arm64 |

Что видно в итоге:

* **дерево** показывает нативный образ отдельным узлом («native image · x86-64 · N methods») со списком
  методов: имя, файл и строка, адрес и размер в подсказке;
* **вкладка** показывает машинный код выбранного метода: `; ── AotTarget.Target.Sum (36 bytes at 0x6c240)`
  и инструкции с адресами, а **связка со строками исходника работает в обе стороны** — курсор в `Target.cs`
  подсвечивает и прокручивает нужный участок листинга, курсор на инструкции подсвечивает строку
  (в статусбаре вместо `IL_xxxx` — адрес);
* **переключатель видов** в такой вкладке предлагает только `Native ASM`: IL и C# там нет, и попытка
  переключиться отвечает причиной, а не пустой панелью;
* методы рантайма, из которого собран образ (их тысячи), по умолчанию скрыты; `ilasmDotnet.nativeIncludeRuntime`
  показывает и их. Если имя образа не совпало ни с одним символом, список показывается целиком, чтобы
  образ не выглядел пустым.

Как открыть: **Open Assembly…** (в диалоге теперь есть `All files` — у AOT-бинаря обычно нет расширения)
или добавить путь в `ilasmDotnet.assemblies`. Открытие из `.cs`-файла пока требует управляемой сборки в
`bin`, поэтому для AOT удобнее дерево.

Проверяется фикстурой `test/fixtures/AotTarget`: smoke публикует её как NativeAOT и проверяет адреса,
размеры, имена, строки и границы блоков; тест расширения — что узел дерева перечисляет методы, что клик
по методу открывает его код и что переключение на IL отклоняется с объяснением.

Ограничения этого маршрута:

* **Linux** (ELF). macOS — тот же DWARF, но контейнер Mach-O, а Windows хранит отладочную информацию в
  нативном PDB (формат MSF), а не в DWARF: это отдельные ридеры, их пока нет;
* нужны **символы**: у полностью раздетого образа (такие есть — например apphost у `ilasm`, который
  лежит в пакете) список методов пуст, и вьюер честно говорит, какого файла не хватает;
* единицы `.debug_info` версии DWARF 5 (в образах это код самого рантайма) не читаются — методы из них
  получают имя из манглинга символа, о чём вьюер сообщает в примечании; `.debug_line` читается и для
  версии 4, и для версии 5;
* методы, которые компилятор заинлайнил, в списке отсутствуют — их кода в образе нет.

## 🎯 Точная связка: attach к живому процессу

Маршрут через харнесс даёт код похожего метода в отдельном процессе. При attach читается **тот
самый код, который исполняет ваш процесс прямо сейчас**, вместе с картой «нативный адрес →
IL-инструкция», которую построил JIT. Отсюда и точность: у каждой инструкции в панели появляется её
`IL_xxxx`, а курсор на инструкции подсвечивает (и позволяет перейти в) ту строку исходника, которую
она реализует.

Что происходит под капотом:

| Шаг | Деталь |
|---|---|
| Процессы | `processes` перечисляет запущенные .NET-процессы (`Microsoft.Diagnostics.NETCore.Client`) |
| Snapshot | по умолчанию берётся дамп `WithHeap` (~68 МБ на тривиальном приложении) — для чтения JIT-кода этого достаточно |
| DAC | ClrMD 4.x ищет DAC через symbol locator и на Linux его не скачивает, поэтому берётся DAC самого рантайма цели — тот, что лежит рядом с загруженным им `libcoreclr` (путь из `ModuleInfo` или из `/proc/<pid>/maps`). Дамп сообщает рантайм как `0.0`, и только для этого случая несовпадение версий DAC разрешается: DAC от другого рантайма остаётся ошибкой |
| Attach | `live/attach` открывает дамп в ClrMD: рантайм, модули, `ClrMethod.NativeCode`, `HotColdInfo` |
| Дизасм | байты читаются из памяти через `IMemoryReader` и декодируются `Iced` (x64) |
| Карта | `ClrMethod.GetILOffset(address)` → `IL_xxxx`; пролог и эпилог отмечаются отдельно |
| Исходник | IL-смещение превращается в строку через PDB той же сборки |
| Кеш | сессия одна на процесс: байты и блоки переиспользуются при переключении вида |

Почему snapshot, а не прямой attach: `ptrace` на Linux по умолчанию ограничен
(`kernel.yama.ptrace_scope = 1`) — отлаживать можно только своих потомков, а расширение не является
родителем вашего процесса. Дамп же пишет сам рантайм по diagnostic-сокету, поэтому работает без
`ptrace` и не останавливает вашу программу. Файл дампа удаляется при detach и при выходе движка.
Версию рантайма в дампе ClrMD отдаёт как `0.0`, поэтому она берётся из `/proc/<pid>/maps`.

Ограничения живого маршрута:

* работает та платформа, на которой идёт рантайм: сейчас дизассемблируется **x64**;
* метод попадёт в панель с точной картой только если он уже скомпилирован: если метода в списке
  нет, панель так и пишет («the method has not been compiled yet; call it first»). ReadyToRun-метод
  может не иметь своего кода вовсе — тогда его встроили в вызывающего;
* для attach нужен PDB сборки: без него будет код и `IL_xxxx`, но не строки исходника.

## 🧩 F#, VB и любой другой язык .NET

Просмотрщик читает **сборку**, а не язык: C#, F#, VB и что угодно ещё компилируются в одни и те же
метаданные, поэтому источник кода — это просто файл, из которого находится сборка проекта. Отсюда
всё, что даёт язык:

| Что | Как |
|---|---|
| Поиск сборки | По ближайшему файлу проекта вверх от файла — `*.csproj`, `*.fsproj`, `*.vbproj` |
| Кнопка в контекстном меню | Условие `editorLangId == csharp \|\| ... == fsharp \|\| ... == vb`: меню появляется и в `.fs`-файле |
| Горячая клавиша | Та же тройка языков, `Ctrl+Alt+I` |
| Связка с исходником | Строки берутся из PDB, поэтому переходы ведут в `.fs`/`.vb` — как в `.cs` |
| Панель C# у F#-сборки | Это C# **того IL**, который скомпилировал компилятор F#: у просмотрщика один декомпилятор, и он читает метаданные. То же и для VB |
| Пересборка после сохранения | Сохранение `.cs`, `.fs` или `.vb` сбрасывает кэш и перечитывает сборку |

Проверено фикстурой `test/fixtures/FsTarget` (F#): IL и C# по файлу, связка со строкой `.fs`,
JIT-листинг, а для образа ReadyToRun — та же карта «инструкция → инструкция IL», сверенная с
рантаймом инструкция за инструкцией.

## 🧊 ASM прямо из образа ReadyToRun

Если сборка опубликована как ReadyToRun, её код лежит в самом файле. Панель ASM читает его
**без процесса и без пересборки**: это ровно тот код, который исполняет приложение, и — главное —
так можно посмотреть код **другой архитектуры**: arm64-образ читается на x64-машине, что маршруту с
attach недоступно в принципе.

Как находится код метода (формат R2R описан в `readytytorun-format.md` из dotnet/runtime):

| Шаг | Деталь |
|---|---|
| Заголовок | у PE есть каталог native header: сигнатура `RRR`, версия формата и таблица секций (тип, RVA, размер) |
| `RuntimeFunctions` (102) | отсортированный список блоков кода: начало, конец (на x64) и указатель на unwind-данные |
| `MethodDefEntryPoints` (103) | sparse array (native format) от строки MethodDef к индексу блока; значение = индекс плюс флаги, и число флаговых бит зависит от младшего бита (нет фиксапа — один бит, есть — два) |
| `DebugInfo` (105) | карта «нативная инструкция → инструкция IL», та же sparse array по номеру блока, а дальше блоб метода |
| Размер на arm64 | в таблице его нет, он берётся из unwind-данных: первые два байта — длина функции в 4-байтовых инструкциях |
| Дизасм | x64 — Iced (как и в живом маршруте), arm64 — Capstone, поэтому архитектура образа и машины могут не совпадать |
| Соседние блоки | тело может состоять из нескольких блоков (funclet или холодная часть): блок, начинающийся там, где кончился предыдущий, относится к тому же методу и помечается в листинге |

### 🧵 Связка с IL из самого образа

В описании формата секция `DebugInfo` помечена как TODO, но кодировку можно прочитать из исходников
рантайма, и теперь она читается: у каждой инструкции листинга из образа стоит её `IL_xxxx`, как и в
листинге живого процесса, а панель связывает строку листинга с инструкцией IL и со строкой исходника
через PDB. Attach для этого больше не нужен — и то же самое работает для arm64-кода, который на
x64-машине иначе не увидеть.

| Шаг | Деталь |
|---|---|
| Где лежит блоб метода | `DebugInfo` — sparse array по номеру блока в `RuntimeFunctions`; значение записи — либо смещение блоба, либо, когда запись записана полным словом, расстояние назад до блоба, лежащего перед ней |
| Заголовок блоба | ниббловые числа: длина части с картой и длина части с переменными; «жирный» заголовок (`0`) добавляет ещё четыре длины, из которых нужна только первая |
| Карта, формат ≥ 16 | в заголовке части — число записей и ширины двух из трёх чисел записи, дальше записи битовыми полями; вид записи — фиксированные 2 бита |
| Карта, формат < 16 | число записей и дальше тройки: смещение от предыдущей записи, `IL_offset + 3` и вид записи — ниббловые числа без выравнивания |
| Точка отсчёта | смещения нативные — от начала блока, поэтому несколько блоков одного тела (funclet, холодная часть) читаются каждый по своей карте |
| Возраст цели | проверено на образах `net6.0`, `net7.0`, `net8.0`, `net9.0`, `net10.0`: у первых трёх секция несёт старую кодировку (форматы 8.0/9.0/9.1), у последних — битовую (16.0), и обе читаются одинаково. Отдельно проверено, что для процесса на .NET 6 листинг из образа и листинг живого процесса совпадают инструкция за инструкцией |
| Проверка | список из образа сверяется с тем, что рантайм отдаёт для того же метода через attach, инструкция за инструкцией — фикстуры `.NET 8` и `.NET 10` проверяют обе кодировки |

Заодно нашлась пара ошибок в соседнем коде, которые теперь закрыты проверками: индекс блока в
`MethodDefEntryPoints` читался как `значение >> 2` всегда, из-за чего метод без фиксапа в записи
получал код соседа (на `.NET 10` так и было: `Countdown` показывал тело `Grade`), и ClrMD метил
инструкцию, начинающуюся ровно там, где кончается диапазон предыдущей записи, предыдущей
инструкцией IL — из-за чего листинг живого процесса и листинг из образа расходились на одну
инструкцию. Оба места читают карту как «последняя запись, начинающаяся не позже адреса» — так же,
как это делает рантайм.

Архитектура образа определяется по полю machine: у
crossgen2 для unix-таргетов оно своё (значения выписаны в коде с комментариями — они были прочитаны
из образов, собранных под каждую платформу), и образ неизвестной архитектуры честно остаётся
маршруту с харнессом.

Про последний случай панель теперь говорит прямо: если в файле есть ReadyToRun-код, а прочитать его
нельзя (архитектура вне поддержки, заголовок нечитаем, кода для этих методов в образе нет), первая
строка листинга называет причину — например «`App.dll` carries ReadyToRun code for linux-arm, which
this build cannot disassemble (x64 and arm64 only)» — и говорит, что код ниже скомпилирован на этой
машине, а не взят из файла. При `ilasmDotnet.asmSource: image` тот же текст приходит как ошибка: раз
источник запрошен явно, тихая подмена была бы враньём.

## 🔁 Сборка IL обратно: ilasm round-trip

`ILASM Dotnet: Assemble the IL Back with ilasm` берёт сборку, открытую в просмотрщике, выписывает её
целиком (манифест, ссылки, все типы и тела) в один ILASM-файл, отдаёт его `ilasm` и сравнивает
результат с оригиналом: число типов, число методов и их сигнатуры должны совпасть. Это единственная
проверка, которая не верит просмотрщику на слово — листинг, который принимает настоящий ассемблер,
это действительно IL.

Что стоит знать:

* **Ассемблер поставляется с расширением** (~7 МБ: linux-x64/arm64, osx-x64/arm64, win-x64).
  `ilasm` из mono не подходит — он не понимает `.interfaceimpl`, который пишет дизассемблер. Свой
  путь можно задать настройкой `ilasmDotnet.ilasmPath`; если заданный путь не существует, берётся
  поставляемый.
* **Обработчики исключений переписываются.** Дизассемблер сокращает их как
  `.try IL_000f-IL_002f finally IL_002f-IL_0039`, а ассемблер ждёт
  `.try IL_000f to IL_002f finally handler IL_002f to IL_0039`. Обе формы, а также `catch <тип>`,
  `fault` и `filter`, проверены на настоящем `ilasm`; тест на фикстуре требует, чтобы листинг с
  `try/catch/filter/finally` собирался.
* Сгенерированный `.il` открывается рядом, чтобы его можно было прочитать и поправить; путь и
  результат видны в сообщении. Файлы кладутся в хранилище расширения, а не в проект.
* Чего round-trip не обещает: побайтового совпадения (токены и раскладка меняются) и полного
  сохранения атрибутов — сравниваются типы и методы. Ошибки `ilasm` показываются как есть, с
  указанием строки листинга.

## 🚧 Ограничения

* Связка **декомпилированной C#-панели** с IL — на уровне члена (метод/свойство), а не строки:
  точные аннотации «узел AST ↔ инструкция IL» в `ICSharpCode.Decompiler` внутренние
  (`TranslatedStatement`, `ExpressionWithILInstruction`) и стираются при рендере текста.
  Связка IL ↔ **ваш исходник** при этом точная, по PDB.
* Компиляторно-генерированные члены по умолчанию скрыты в высокоуровневой C#-панели, но видны в IL и
  в низкоуровневом виде — для них подсветка высокоуровневой панели не сработает (это ожидаемо).
* Низкоуровневый вид — это вид декомпилятора, а не дизассемблера: он показывает конструкции языка,
  в которые компилятор разворачивает сахар, но не отдельные инструкции IL. Инструкции — это вид IL.
* Debug-сборки декомпилируются с артефактами вида `if (1 == 0) { }` — это особенность
  неоптимизированного IL, а не ошибка просмотрщика.
* Панели доступны только для чтения.

## 📮 Упаковка

```bash
npm run package     # dist/ilasm-dotnet-1.0.0.vsix
code --install-extension dist/ilasm-dotnet-1.0.0.vsix --force
```

В пакет попадают бандл расширения, опубликованный движок, грамматики, иконка и два нативных
компонента: `ilasm` для пяти платформ и `libcapstone` для дизассемблирования arm64. Capstone
поставляется для девяти платформ, но нужны только пять целевых, поэтому остальные исключены в
`.vscodeignore` (иначе пакет вырастает на 20 МБ). Исходники, тесты и `node_modules` исключены
там же. Движок публикуется с `UseAppHost=false`,
поэтому в пакете нет платформо-зависимого файла, но нужен установленный **.NET 10 runtime**.
Движок не привязан к своей целевой платформе жёстко: `RollForward=LatestMajor` позволяет ему идти
и на более новом рантайме, если он установлен вместо десятого.

Движок — это ещё и JIT-харнесс: он запускает себя же дочерним процессом с переменными
`DOTNET_JitDisasm` и `RuntimeHelpers.PrepareMethod`, и сборку под анализ грузит именно тот рантайм,
который исполняет харнесс. Поэтому целевая платформа движка (`net10.0`) — это и есть та версия
рантайма, кодом которого отвечает маршрут «ASM от JIT».

Фикстуры тестов идут на .NET 10, кроме одной: `test/fixtures/LiveTarget` остаётся на **net8.0**.
Так проверяются сразу две вещи, которых на десятом рантайме не получить: attach к процессу более
старого рантайма и **старая кодировка карты** «инструкция → инструкция IL» в R2R-образе — кодировка
следует целевой платформе сборки, поэтому образ для net8 несёт формат 9.1, а для net10 — 16.0, и
ридер проверяется на обоих.

## 🔭 Что осталось

* 🚧 **Другие кодировки карты**: `.NET 8` и `.NET 9+` читаются (9.1 и 16.0 проверены фикстурами), а
  более старые образы (и «жирные» блобы с дополнительными частями) — нет: для них листинг остаётся
  связанным по методу.
* 🚧 **NativeAOT для других платформ**: Linux сделан. macOS — тот же DWARF в контейнере Mach-O,
  Windows — отладочная информация в нативном PDB вместо DWARF; каждому нужен свой ридер.
* 🚧 **Единицы DWARF 5 в `.debug_info`** (в образах AOT это код самого рантайма) пока не читаются, их
  методы называются по манглингу символа — см. [NativeAOT: ASM без IL](#-nativeaot-asm-без-il).
* 🚧 **Другие архитектуры**: Capstone умеет arm32, x86 и riscv — сейчас из них не поддержан никто,
  потому что не поддержаны их таблицы R2R.
* 🚧 **Мелочи**: кеш панелей на диск, публикация в Marketplace, проверка именно установленного
  расширения (in-host тесты запускаются на распакованном пакете).
* 🚧 **Мультицелевые проекты**: `<TargetFrameworks>net8.0;net10.0</TargetFrameworks>` — берётся самая
  свежая сборка из `bin/**`, а не та, что выбрана в IDE.

## 🔐 Приватность

Расширение не делает сетевых запросов: ни телеметрии, ни отправки сборок, исходников или дампов.
Ни в расширении, ни в движке нет ни одного сетевого вызова — тяжёлая часть считается локально,
общение с движком идёт по stdio, а дочернему `dotnet` явно выставлен `DOTNET_CLI_TELEMETRY_OPTOUT=1`,
чтобы не сработала телеметрия самого CLI (`Views/AsmViewService.cs`).

Читается только то, что вы открыли: сборка, её portable PDB, при необходимости `.dbg`/DWARF рядом с
нативным образом и процесс, к которому вы подключились командой Attach. На диск расширение пишет
только свои артефакты: сгенерированный для round-trip `.il` в хранилище расширения и распакованный
single-file бандл во временный каталог.
